# Спільнота колекціонерів — затверджена архітектура

Статус: **специфікація, серверна реалізація ще не підключена**.

## Модель доступу
- **Гість (за замовчуванням):** усі чинні функції каталогізації доступні без реєстрації та інтернету; локальна IndexedDB зберігається без змін.
- **Зареєстрований користувач:** добровільний вхід для синхронізації, профілю, підписок, спілкування, обміну. Не блокувати гостьовий каталог через збій сервера.
- **Нікнейм + пароль без обов'язкової пошти:** лише через серверний auth-бекенд; не зберігати паролі в таблицях або IndexedDB. Для Supabase Auth потрібен окремий перевірений спосіб реалізації username-login (наприклад, власний auth endpoint з серверною перевіркою та сесіями): простий фіктивний email-аліас не є підтвердженою адресою і не має використовуватися як канал відновлення.
- **Відновлення:** одноразові резервні коди, серверне зберігання тільки хешів. Показати коди один раз і запропонувати зберегти. Передбачити регенерацію з активної сесії.
- **Приватність:** нові акаунти, колекції, фото, місцеперебування та бажанки приватні за замовчуванням. Публікація лише за окремою чіткою дією користувача.

## Міграція / синхронізація
1. До першого входу запропонувати експорт локальної резервної JSON-копії.
2. Створення акаунта **не змінює** локальну IndexedDB.
3. Після входу показати попередній перегляд: скільки папок, предметів і фотографій буде синхронізовано; потрібна окрема згода.
4. Використовувати стабільний локальний UUID для дедуплікації; upsert лише в межах user_id. Конфлікти вирішувати без втрати даних, з попереднім переглядом.
5. Синхронізовані приватні дані не стають публічними. Вітрина — окрема whitelist-модель (published_item_ids / approved_public_fields).
6. Режим офлайн продовжує працювати. Вихід з акаунта не повинен непомітно видаляти локальні записи; для спільних пристроїв потрібен чіткий вибір очищення локального кешу.

## План таблиць PostgreSQL
- profiles(id, handle, display_name, avatar_path, bio, created_at, visibility)
- collections(id, owner_id, parent_id, title, metadata, updated_at)
- collection_items(id, owner_id, collection_id, catalog_key, metadata, updated_at, visibility)
- follows(follower_id, followed_id, created_at)
- conversations(id, created_at)
- conversation_members(conversation_id, user_id)
- messages(id, conversation_id, sender_id, body, created_at)
- trade_offers(id, proposer_id, recipient_id, offered_item_id, requested_item_id, status, created_at)
- blocks(blocker_id, blocked_id), reports(id, reporter_id, subject_id, reason, status)
- recovery_codes(user_id, code_hash, used_at, created_at) у захищеній серверній схемі

## Безпека й модерація
- Row Level Security: власник читає власні приватні дані, публічні записи доступні тільки через явно дозволені поля.
- Повідомлення доступні лише учасникам діалогу; блокування й скарги повинні працювати до загального запуску чатів.
- Rate limiting для реєстрації, входу, відновлення, повідомлень та запитів дружби.
- Фото: перевіряти тип/розмір, обмежувати доступ до приватного Storage; очищувати EXIF/геомітки для публікацій.
- Видалення акаунта, експорт даних, контроль видимості.
- Жодних service_role keys, паролів чи секретів у GitHub Pages / frontend.

## Етапи
1. Схема БД, правила RLS, auth endpoint, реєстрація за нікнеймом, резервні коди (потребує налаштованого серверного проєкту).
2. Добровільне прив'язування локального каталогу, безпечна синхронізація, профіль і публічна вітрина.
3. Пошук колекціонерів, підписки, особисті повідомлення, блокування та скарги.
4. Обміни, клуби, стрічка.

## Принцип релізу
До перевірки auth + RLS та реального тестування міграції соціальні функції не показувати як працюючі. Наявний каталог повинен залишатися працездатним без сервера.
